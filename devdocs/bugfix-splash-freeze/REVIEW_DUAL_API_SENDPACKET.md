# REVIEW_DUAL_API_SENDPACKET.md — 补充评估：同步+异步双 API 收益风险模型（CodeArts MSG8 任务书）

> 2026-09-17。承接 `REVIEW_ASYNC_SENDPACKET.md`（MSG7 评估）。**先修正评估基线**：锁内长计算的真凶（每帧 32MiB 缓冲）已被 omp `f872b99` 消除——本评估按「`f872b99` 后 sendPacket 同步等待回落到微秒~毫秒级」的新基线作答；若真机复验未归零，则按旧基线（锁竞争仍在）重读 §3.4。

## 3.1 分类评审：**大方向正确，三处修正**

CodeArts 的两类划分（用户操作→同步收益 / 自动周期→异步收益）方向正确，但有三处要点：

1. **「同步收益」多数是伪需求**：逐点核对调用方代码后，所谓「点击即反馈」实际分两种——
   - **本地即时反馈**（弹窗关闭、图标切换、状态置位、toast「已发送」）：这些 UI 变化在 `send()` 返回**之前**就由调用方代码完成或根本不依赖返回值——`boolean ok` 只用于日志/失败 toast。异步化后 UI 反馈**分毫不少**（UI 更新本来就不等网络）；
   - **对端响应反馈**（配对接受、MPRIS 状态变化、响铃）：同步等 sendPacket 返回也**换不来对端响应**——响应走 packetReceived 事件（异步），同步发送只是把「请求发出」提前几毫秒。**没有任何一个调用点真正依赖「同步完成」本身**；
2. **遗漏场景：配对竞态路径（PacketRouter:175）不是「低收益异步」而是「顺序敏感」**——它与 :81/:94/:103 共享 `requestedPeers` 状态机，四个 pair 调用点必须**保持相互之间的入队顺序**（MSG7 已裁定 sendPacket 路径含配对，此为源码事实）；`ping` 回显（PingPlugin:24）同理——回显延迟会触发对端重发/超时，协议层有副作用；
3. **周期包的真正收益点认可以下三个**：battery:77 / connectivity_report:70 / mpris:141（建链即发）——它们与「用户操作」争抢的不是「同步性」而是**发送顺序**（identity→通告→插件的会话顺序）。

### 修正后的分类本质

> 「同步收益高」的调用点 = **用户可感知的交互动作**（需要确定的提交语义）；「异步收益高」= **建链突发期的批量通告**（需要不阻塞主线程）。而这两类在 `f872b99` 之后**都不再被阻塞**——分类是给「若阻塞未归零」的兜底方案用的。

## 3.2 双 API 可行性：**NAPI 层面可行；实现选项有明确优劣**

- **两个独立导出函数（推荐）**：`sendPacket`（同步，语义=已入队）+ `sendPacketAsync(deviceId, json): Promise<void>`——NAPI 侧 Promise 用 `napi_create_promise` + 任意线程 `napi_resolve_deferred`，网络线程入队成功后 resolve、失败 reject；**两个函数共享同一个 native 发送队列**，顺序契约在队列层统一保证；
- **flag 参数（不推荐）**：一个导出函数带 async flag——返回值类型随参数变化（boolean|Promise），ArkTS 侧类型收窄丑陋、d.ts 表达别扭，且调用方错误使用 flag 的可能性更高；
- **ArkTS 侧区分方式：由调用方显式选择（推荐）**，不建议按 packet type 自动路由——自动路由把「哪类包走异步」的策略埋进 native/桥层，将来插件调整周期策略时要改桥层；显式选择让策略留在插件作者手里，审查可见。

## 3.3 收益风险模型（与全异步+Promise 链对比）

| 维度 | 双 API | 全异步+Promise 链 |
|---|---|---|
| 开屏期主线程释放 | ✅ 三个周期包不占 JS | ✅ 同 |
| 顺序契约 | ✅ 两 API 共享 native 队列，**单点保证** | ⚠️ per-device Promise 链放 JS 纪律，插件一多必漏 |
| 返回值契约破坏 | ✅ 现有 `sendPacket():boolean` **零改动**（10+ 插件不动） | ❌ 全部调用点改 async/await |
| 调用方选错风险 | ⚠️ 存在（新人可能给用户操作选 async）| ✅ 无选择即无选错 |
| 维护成本 | ⚠️ 两个导出+一套队列 | ⚠️ 链生命周期管理（页面重建/设备断开时链的清理） |
| 可回退性 | ✅ 异步出口是**增量**，弃用即删 | ❌ 破坏性变更，难回退 |

**结论：双 API 严格优于全异步+Promise 链**——收益相同、契约破坏为零、顺序保证单点化。MSG7 评估中「窄版」与本评估「双 API」实为同一方案的两种表述，本份把它落到 API 形态。

## 3.4 轻量替代方案评审

1. **「锁竞争时降级异步」（tryLock 失败返回 Promise）：不推荐**——同一函数返回两种类型（boolean|Promise）在 ArkTS 侧无法静态区分，每个调用点都要写 `if (result instanceof Promise)`，10+ 插件全量污染；且 tryLock 失败瞬间恰恰是网络线程最忙的时刻，此时把发送甩给异步线程再加队列，时序行为最难推理；
2. **「仅建链突发期走异步」：可行但判定器多余**——「突发期」可以用**确定性规则**定义（`Encrypted` 后 N 秒内 / 首批 3 个通告包），不必动态判定；但这正是双 API 想做的事（插件作者在「建链即发」的调用点显式选 async），加自动判定器只会引入第二套策略。**结论：与其做判定器，不如双 API 显式标注**；
3. **真正的零成本替代（`f872b99` 后的主路线）**：如果真机复验确认慢发送已归零，**什么都不做就是最优解**——同步 API 保持现状，等待 MS 级等待不构成用户可感知卡顿。

## 3.5 最终建议

**分两个时间点作答**：

- **现在（`f872b99` 真机复验前）**：不动手。复验归零 → 本提案整个关闭；未归零 → 进入下一行；
- **若复验仍有秒级慢发送**：做**双 API**（两个 NAPI 导出、共享 native 队列、显式选择），首批只给三个建链通告包（battery/connectivity_report/mpris.requestPlayerList）换 async 出口——影响面 3 个插件文件 + d.ts 增量，配对/MPRIS/命令等用户操作路径**保持同步语义不动**；全异步、条件降级、自动路由均不推荐。

**优先级**：双 API 排在 ① 锁修复复验 ② CN 校验 之后（它是兜底方案，触发条件依赖前两者的结果）。
