# REVIEW_HOLISTIC_BUGFIX.md — BUG 修复链全量评审：整体性/标准化视角（AtomCode）

> 2026-09-17。范围：开屏卡顿专项全部 14 枚 commit（`8417d29`→`42f5891`）+ 配套 Rust/ArkTS 改动。视角：**整体性、标准化开发**——不以「对不对」为准（对错已在前序评审闭环），而以「**结构是否该这么长、机制是否重复、临时件是否该退场**」为准。

## 一、总体判断

**修复链本身质量高**：定位数据驱动、每步有验证、文档与经验同步沉淀。但以标准化视角看，本次 BUG 处理在 native 层留下了**三类结构性债务**——它们不是 bug，而是「补丁式演进」的自然产物；若不收编，下一个人在 `net_stack.cpp`（已 1600+ 行）上叠加任何功能都会重蹈本次的排查成本。

## 二、结构性发现与优化路线（按优先级）

### S1（P1）：`dispatchFrames` 的锁内职责过载——应拆「锁内提取/锁外解析」

现状：`dispatchFrames` 在 `connMutex_` 临界区内完成 **帧提取 + cJSON 解析 + identity 钉扎比对（trustMutex_ 嵌套）+ 链路替换决策 + 派发**（net_stack.cpp:1196–1260+）。`f872b99`/`105ddff` 把它的 CPU 从秒级压到了毫秒级，但**结构没变**：临界区长度仍与「单帧 JSON 大小 × 帧数」成正比，将来任何解析路径的性能回归都会重新变成全 UI 冻结。

**标准化形态**（两阶段管线）：
```
锁内：extractFrame + 帧 → 无锁队列（per-connection deque 即可）
锁外（网络线程内，不持 connMutex_）：cJSON 解析 + 决策 → 需要动连接状态时短临界区回写
```
cJSON 解析不需要 connMutex_ 保护的对象（frame json 是局部拷贝）；真正需要锁的只有「deviceId 写回/钉扎/替换」这几个决策点。收益：临界区从「解析耗时」退到「决策耗时」（微秒级），锁竞争类别的问题**结构性绝迹**而非靠性能修复压制。规模：~150 行重构 + 既有 31 用例回归。**建议作为下一个独立 commit**（与「解析移出锁」的旧候选合流——omp 评审时说「暂不做，设计保留」，本评审将其升级为 P1：不是为性能，是为结构）。

### S2（P2）：`connMutex_` 临界区内的 4 处 LOGE/LOGI 应全部移出

粗查 dispatchFrames/drainEncrypted 段仍有 4 处同步日志在临界区内（`invalid JSON frame dropped` 等）。单次 hilog 调用虽快（µs 级），但在「锁内工作最小化」的标准化口径下，日志属于「与连接状态无关的 I/O」——应改为先把消息攒到局部 string，出临界区后统一打。规模：~20 行。与 S1 同批顺手完成。

### S3（P2）：两套「EPOLLOUT 按需挂/摘」实现应提取公共设施

连接侧（`NetStack::updateWriteInterestLocked` + `WriteInterestGuard` RAII）与 payload 侧（`PayloadManager::updateWriteInterestLocked` + 局部 InterestGuard struct）是**同一机制的两份手写拷贝**——判据构造（pending||tls wantsWrite||握手未完成）、armed 缓存、MOD 调用、RAII 刷新点，四处逻辑重复，且**两份注释各自记载了同一教训**（「刷新点必须与状态推进同址」「不得纳入 SENDAPP」）。这正是 omp 三次修复失败付出过学费的地方——机制散写两份意味着第三次踩坑的可能是第三个新 fd 类型（未来 payload listen fd 等）。

**标准化形态**：提取 `EpollWriteInterest` 小类（持有 epollFd + fd，封装 want 判据回调 + MOD + RAII guard），两侧改组合使用。规模：~80 行新设施 + 两侧各 ~30 行改接。**收益是防回归而非减行数**。建议排在 S1 之后。

### S4（P2）：埋点系统性收编——32 处埋点应有「常驻/排查」两档

本次专项在 native 层累计了 **32 处埋点代码**（net_stack 32 个标识 + payload/napi 若干）：`JsEntryTimer`、`JsLockWait`、`NETLOOP`、`PHASESPLIT`、`DRAINSPLIT`、`FRAMESPLIT`、`PAYLOAD`、事件普查、锁内分段计时……它们逐个都有价值，但：
1. **常驻成本已不可忽略**：每帧的 census 计数、每 tick 的分段计时都在热路径上，虽轻但乘上 1 万次/秒迭代；
2. **排查语义已固化**：这些埋点的使命（定位锁内长计算）已完成（omp 经验文档已沉淀）；
3. **无开关**：全部是裸 LOGI/裸计数，release 包与排查期无差别。

**标准化形态**：引入 `KDC_TELEMETRY` 编译期开关（release 默认只留 `NETLOOP` 粗粒度 + `JsEntryTimer`/`JsLockWait` 两个用户可见性哨兵，其余 debug-only）；或运行时 sysprop 开关。规模：~50 行宏改造。**建议随 S1/S2 之后的独立 commit**，专项关闭前完成——否则这批「排查完就该退场的仪器」会永久留在热路径。

### S5（P3）：`net_stack.cpp` 单文件 1600+ 行应拆分

事件循环 + UDP/TCP 事件处理 + 配对决策 + 信任表 + payload 桥 + 统计埋点全在一个 TU。本次排查反复出现的「在同一文件里跳 400 行看上下文」就是信号。建议按已有头文件边界拆：`event_loop.cpp`（循环+统计）/ `connection_io.cpp`（readable/writable/drain/dispatch）/ `pairing.cpp`（identity/pair/替换）。**纯移动不改逻辑**，随 S1 重构自然完成一半。

### S6（P3）：ArkTS 侧 `Index.ets` 同病（2500+ 行）

事件处理 + 插件宿主接线 + UI 状态 + MPRIS 面板 + 日志系统在同一页面组件。卡片忙碌态（`42f5891`）又在往里加。DevEco 已认领根治清单 #1–#5，建议在其上补一条「Index.ets 拆 Tab 子组件 + 事件总线」的结构项，与omp 侧 S5 对称。

## 五、一句话结论

本次 BUG 处理的**每一次修复都正确，但正确性是靠「在旧结构上越叠越精巧」换来的**；`net_stack.cpp` 的锁内职责、两套写兴趣、32 处埋点三笔债不还，下一种锁竞争问题（或下一个 fd 类型）会把今天的排查成本原样重收一遍。建议把 S1–S4 作为「专项关闭条件」随本迭代执行，让专项以**结构收编**而非「现象消失」收官。
