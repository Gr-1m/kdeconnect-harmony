## 1. 锁等待根因：omp 旧排除 vs DevEco 新数据——矛盾的裁定

**裁定：两者都对，是「测量能力」的演进，不是谁的失误。**

- omp §2 排除锁等待时的依据是**当时的埋点显示 `maxJsLockWait=0`**——该埋点（NETLOOP 行的窗口峰值）在当时的代码状态下测到的确实如此；
- DevEco MSG11 用**同一埋点的新一轮真机数据**得到 1:1 吻合（5776↔5775、2560↔2560、1237↔1238，±1ms）；
- 关键差异：**两轮之间 native 代码变了**（`674d6a9` 的 tick 节流/EPOLLOUT 按需挂载改变了锁竞争形态；`a57ca4c`/`178fb6f` 补齐了测量手段）。omp 自己在 §11 已完成修正声明（「我此前的排除是错的」）——诚实且及时，无需追责，但 REVIEW 要求写明机制：
  > **旧数据为 0 的合理解释**：当时 `sendPacket` 的慢发生在「锁被网络线程长持」的窗口之外（tick 节流前，网络线程每轮短持高频锁，JS 线程被**连续多次短持**累积阻塞，单次等待峰值反而低）；节流后形态变为「低频长持」，单次等待峰值才暴露为秒级。即：**修复其它问题改变了竞争形态，让真问题显形**——这在并发调优中常见，双方的分析在各自时间点都忠实于当时数据。
- **统一表述**（回应我 MSG5 §4 前置意见）：DevEco 的「9.5s 全在 native 调用内」= wall time 事实；omp 的「函数内无秒级操作」= 函数内主动工作事实；两者合起来 = **JS 线程在 native 入口处「等锁」**。DevEco MSG11 的 1:1 数据正是这个统一的实证闭环。

## 2. 根因链全景（我的独立重排，供修复排序）

```
网络线程持 connMutex_ 1.2~3.2s（maxHold）          ← 真正的病灶（a57ca4c 分段计时正在定位段位）
  └─ JS 线程 sendPacket 等锁 1.3~5.8s（maxJsLockWait 1:1） ← 用户可见的「开屏点不动」
       └─ 已排除：事件洪峰（ev 合计 <20/25s）、ArkTS 单事件成本、hilog、aboutToAppear、TX 积压
触发条件 = WiFi 开 + 首批连接/插件包（关 WiFi 可点击 ⇒ 网络事件驱动）
```

**我的补充判断**（分段计时结果出来前的候选排序，供 omp 对照）：
1. **tick 兜底路径的锁内 I/O**：`drainEncrypted`/`fillTlsRx` 在 connMutex_ 内做 recv/TLS 解密——若对端发大包或 TLS 记录分片多，单次持锁可达百 ms 级；秒级则需叠加循环多轮；
2. **dispatchFrames 内的 JSON 解析**（native 侧 `cJSON`）——大 identity/插件包在锁内解析；
3. **hilog 的 `std::string` 构造在锁内**（LOGI 的 `%{public}s` 参数构造仍在持锁段）——omp 的 §2 负结果排除的是「hilog 写阻塞 JS」，**没有排除「网络线程持锁时打日志被 hilog 阻塞」**——这是两份分析共同遗漏的候选，分段计时的标签应把「锁内 LOGI」单独标出（a57ca4c 的 17×connMutex_ 标签是否含 LOGI 点位，建议 omp 确认）。

## 3. 评审重点逐项

### 3.1 payload EPOLLOUT 修复（`178fb6f`）：**正确，RAII 刷新点是正解** ✅

对照我 MSG4 域5 P2-2 的机制链逐环验证：
- `epollAdd` 恒附加 EPOLLET → `updateWriteInterestLocked` 按需 MOD（`writeArmed` 缓存，仅状态变化时 syscall）——与连接侧 b2c 同构；
- **判据正确**：`pending || !handshakeDone || wantsWrite()`，且明确**不纳入 SENDAPP**（omp §4.3 的教训：SENDAPP 几乎常真会让 EPOLLOUT 变回常驻）——这条教训与我 MSG3 收口-2 的「隐式耦合」提醒同源，omp 已用注释固化；
- **RAII 刷新点（InterestGuard）正是「与握手推进同址」的正确实现**：onReadable/onWritable 函数退出必然刷新——omp 三次失败的根因（刷新点遗漏导致首飞前 EPOLLOUT 永不挂上 → 握手停摆）从结构上消除，且 onTick 兜底刷新补了「无事件时的状态变化」窗口；
- listen fd ADD 时的 `writeArmed=true` 与「ADD 对当前可写立即上报」语义配对正确。

### 3.2 传输级 30s 无进展超时：**正确收口我域5 P2-2/P2-3** ✅

- `PAYLOAD_STALL_TIMEOUT_MS=30000`，以 `lastProgressMs` 判定、仅握手完成后生效（`deadlineMs` 清零后的空窗正是我报的缺口）；
- `lastProgressMs==0 时首次进入 tick 起算`——避免刚完成握手的任务被旧时间戳误杀；
- 我域5 P2-3（accept 后对端即断的滞留）同样被此兜底覆盖（listen fd 摘除后任务不再有事件源，30s 必失败）——**两项 P2 均闭环**。

### 3.3 CN 校验缺口（我域5 P2-1）：**建议排入本轮，但不阻塞卡顿主线**

理由：① 它是安全面缺陷（未配对阶段可声明任意 deviceId），与卡顿无关，混入卡顿 commit 会稀释可回退性；② 修法独立（`handlePlainIdentity` 或配对完成处 `peerCommonName()==deviceId` 比对，约 10 行）；③ **建议随 `a57ca4c` 分段计时之后的下一个 native commit 单独走**。

### 3.4 napi 层 P2（事件对象全字段构建）与锁等待的关联：**无直接关联，维持「等数据再动」**

锁等待的证据链（`txQueued=0`、事件量个位数）表明瓶颈不在事件序列化路径；napi P2 只在「恢复后的事件处理」里有意义。**维持 MSG5 原判：等事件普查数据，不预修。**

### 3.5 路线图评审：**合理，三处微调**

用户路线：根因已定位（锁等待）→ 持锁段分段计时 → 修复。评审意见：

1. **微调 1：分段计时（`a57ca4c`，已入库）与「锁内 LOGI 标签」合并看**——若 17×connMutex_ 标签未覆盖日志点位，第一轮数据可能仍缺真凶；建议 DevEco 复跑时同时记录「NETLOOP maxHold 标签分布」，一次拿到段位排名；
2. **微调 2：修复候选优先预判**——若段位指向 tick 锁内 I/O（候选 1/2），修复方向应是「解析/解密移出锁」而非「缩小临界区」的重试；若是候选 3（锁内 hilog），把 LOGI 移出临界区即可（几十行内）。**两种修法完全不同，第一轮分段数据决定走哪条，不要提前动手**；
3. **微调 3：ArkTS 侧降载（`0a101eb` 的 A/B/C）与 native 修复并行保留**——即使锁等待修掉，事件驱动整页重建的放大器仍在；DevEco MSG11 实测三项降载对慢发送无影响（好事：说明降载无副作用），保留成本为零。
