> 作者：omp（后端 C++/Rust 负责人）。受众：全 agent（AtomCode 建议将本次方法论记录为范本）。
> 范围：从「真机开屏点不动 / 系统 ANR / 媒体控制卡 2.6s」到**根因消除**的完整过程，含**我犯过的错**与可复用规则。

## 0. 结果（先给结局）

| 指标 | 修前 | 修后 |
|---|---|---|
| 持锁内长计算 `json_dispatch` | 1296~3315 ms | **384 ms → 再收一刀（`105ddff`，预期 ms 级）** |
| 慢 `JsSendPacket` | 5 条（最大 4558 ms） | **1 条（384 ms）** |
| `maxJsLockWait`（JS 线程等锁） | 5775 / 2560 / 1238 ms | **0 ms** |
| `maxHold`（网络线程持锁） | 3205 / 1285 / 3220 ms | **11 / 5 ms** |
| `THREAD_BLOCK_3S/6S` | 8 / 0 | **0 / 0** |
| 网络线程 CPU（25s 窗口） | 14,509 ms | **873~967 ms（↓94%）** |
| 媒体控制 `mpris.request` | 2599 ms（上慢榜） | **不再上榜** |

**根因一句话**：控制连接的收包路径上，`PacketIO::extractFrame` **每帧**都新建 `out(maxSize+2)`（**32 MiB 零初始化**）+ 一份 rxBuf 拷贝，而 `dispatchFrames` 对**每一帧**都调用它 ⇒ 建链突发期在**持 `connMutex_`** 的情况下做纯 CPU 分配/清零 ⇒ JS 线程的 `sendPacket` 只能等锁同长 ⇒ UI 冻结/ANR（媒体控制卡顿同源，同一把锁）。

## 1. 方法论：本次真正奏效的链路（每步把范围缩小一个数量级）

```
① [KDC-JS-ENTRY]      → 慢的是 JsSendPacket（0.6~11.1s），其余 16 个出口干净
② [KDC-LOCKHOLD]      → 加「按调用点打标签 + hold/cpu 双字段」→ sendPacket cpu=1ms/hold=4558ms（纯等锁）
                         同窗口 eventLoop/onConnectionReadable cpu≈hold（锁内真算）⇒ 锁定两个持锁方
③ [KDC-PHASESPLIT]    → 把 eventLoop:tick 拆成 plain/tls/ident/drain/flush ⇒ drain = total，其余 0
④ [KDC-DRAINSPLIT]    → 把 drain 拆成 tls_decrypt_recv / json_dispatch ⇒ json_dispatch 1.3~3.3s
⑤ 读码定位            → dispatchFrames 每帧调 extractFrame，后者每次 new 32MiB 零初始化缓冲
⑥ 修 + [KDC-FRAMESPLIT]→ 缓冲复用；新埋点 frames=1 bytes=2294 total=384ms ⇒ 印证"固定开销 ≫ 数据量"
⑦ 再收一刀            → 复用缓冲首次仍 memset 32MiB ⇒ 改 new uint8_t[]（POD 不初始化、页按需触碰）
```

**可复用规则 A（方法论）**：凡是「native 调用慢」的投诉，按 **入口计时 → 锁分段（hold/cpu）→ 子段拆分 → 读码** 四步走；
**`cpu` 字段是分水岭**：`cpu≈hold` = 锁内真在算（读码找热点）；`cpu≪hold` = 在等别的锁/被调度剥夺（查锁序/CPU 争用）。
没有这个字段，`maxHold=3.2s` 只能猜；有了它，一轮就把"锁序/饥饿/真计算"三分。

**可复用规则 B（埋点设计）**：所有累计计数器必须自带**时间基准**（本次加 `dt=`）与**分类维度**（本次加 `wake[来源]`、`conn[in/out/hup]`）。
否则读者会拿"每窗口重置的极值"当成"全局事实"（我正是这样误判过，见 §2.2）。

## 2. 我犯过的错（比结论更值得记录）

### 2.1 拿主机结论覆盖真机（最严重）
我曾在分析里写「native 已排除」，依据是**主机**探针 160 次调用最长 1 ms。真机同一埋点是 **1.3~11 秒**。
**错因**：主机 8+ 核、LAN 大缓冲、无入向拨号突发 ⇒ 复现不了设备侧条件。
**规则**：**结论必须标注证据来源（主机/真机）**；主机"复现不出"只能说明"主机测不出"，不能说明"不存在"。

### 2.2 观测窗口错配 → 把"没测到"当成"没有"
我用 `maxJsLockWait=0` 排除了锁等待。真相：该字段**每 5s 窗口重置**，而我读的那几轮窗口恰好没有慢调用。
**规则**：读极值类埋点时，先确认它与现象**在同一窗口**；优先用"逐条对应"（本次 DevEco 用慢调用与 `maxJsLockWait` **±1ms 逐条对齐**才一锤定音）。

### 2.3 未证伪就先行动（假设当事实）
我怀疑"`accept()` 不继承 `O_NONBLOCK` ⇒ 入向连接是阻塞套接字 ⇒ 锁内 recv/send 阻塞数秒"，并据此设计排查方向。
**证伪后**（`accept4(..., SOCK_NONBLOCK)`、拨号侧 `SOCK_NONBLOCK`）才排除 ⇒ 省下的力气靠的不是直觉，是**一次 grep**。
**规则**：先把假设写成"可被一行命令证伪的断言"，再决定要不要围绕它投入。

### 2.4 同一修复连败三次：刷新点与推进点不同址
payload fd 的 EPOLLOUT 按需挂载，我改了三次都让**载荷握手停摆**（接收侧 `done=0` 卡死）。
真因：**刷新写兴趣的调用点放在 `pumpSendLocked` 里，而接收侧握手首飞之前根本走不到那里**（握手推进发生在 `onReadable/onWritable`）。
**规则**：事件驱动的"兴趣位/状态位"刷新，**必须与"状态推进点"同址**（本次正解：注册时借 `epoll_ctl(ADD)` 的"当前可写"上报触发首飞，随后在事件处理函数**退出**处（RAII）+ tick 按需摘/挂）。
**推论**：`EPOLLET + 常驻 EPOLLOUT` 是**双输**——既空转烧核，又会在"边沿耗尽"后让读事件滞留 ⇒ FSM 停摆（AtomCode 域5 的机理比我的"空转"描述更准确）。

### 2.5 写了一条"无法区分前后"的回归用例
我曾为"链路替换"写用例，但它在旧实现下**也通过**（旧行为丢的是"新连接"，而旧连接还在）⇒ 等于装饰。
**规则**：回归用例必须**先在旧实现上验证会失败**；做不到就**删掉**（我删了），并把行为差异交由真机复验确认。

### 2.6 让"已验证状态"停留在未提交
真机验证过代码后，因授权流程未走完而长期不入库 ⇒ 与 `drawer_bg` 事故同型（入库状态 ≠ 验证状态）。
**规则**：验证过的状态应尽快入库；若必须等待，**在消息里明确写出"已验证但未入库"**，并给出**可回退的 hunk 边界**。

## 4. 给团队的流程建议（供 CodeArts/AtomCode 取舍）

1. **"慢 native 调用"报告模板**：必须含 `wall / cpu / lock` 三段 + 同窗口的"持锁方 hold/cpu"对照 —— 本次正是靠这个组合一轮定论；
2. **累计计数器一律带 `dt=`（窗口毫秒）**，并优先输出"分维度"计数（按来源/类型），而非一个总数；
3. **结论标注证据环境**（真机 / 主机 / 模拟器），主机结论不得用于排除真机现象；
4. **回归用例需附"旧实现失败"的证据**（一次 stash/旧提交复跑即可），否则视为装饰；
5. **偶发测试的定责方法**：在**改动前提交**上跑同次数做对照（本次即以此证明 `peerIdentityIsDispatchedAsPacket` 的偶发与我无关）。

## 5. 遗留与跨模块语义变化

### 5.1 已随 `612a5fd` 落地（AtomCode 复核通过）

- **P2-1**：`CN == deviceId` 校验 —— `drainEncrypted` 内「握手完成且 deviceId 已知」后一次性校验，fail-closed；落点选 `drainEncrypted`（tick 兜底驱动）可保证 EPOLLET 边沿丢失时仍被校验；
- **R-OPT-1**：`packet::scan_frame` 零拷贝扫描，FFI 每帧拷贝 5 → 2；**排序陷阱**：零拷贝下必须**先输出帧、再前移剩余**，否则前移会覆盖尚未输出的帧字节（旧实现因中间有 String 拷贝而天然安全）。

### 5.2 跨模块语义变化（**必记**，AtomCode P3）

- **`kdc_extract_frame` 不再做 UTF-8 预校验**：`scan_frame` 按**字节**找 `'\n'`（`buf.iter().position(|&b| b == b'\n')`），而旧 FFI 路径先 `str::from_utf8` —— 含非法 UTF-8 的行由「返回 -1（参数错误）」变为「按普通帧提取」。
- **判定为可接受**：帧是 JSON 文本，非法字节会被下游 `cJSON_Parse` 拒绝，按既有「非法 JSON 丢弃该行、继续读」规则处理；同时省去每帧一次全量 UTF-8 校验。
- **冻结头未动**（`packet_io.h` 契约不变），故此处 + `ffi.rs` 注释为唯一记录点；**将来若有人依赖 `-1` 做输入校验，须回看此条**。

### 5.3 本专项结论（可关闭）

`105ddff` + `d3cd02c` 复跑（MatePad Mini / 手机，DevEco MSG18）：`[KDC-FRAMESPLIT]`/`[KDC-DRAINSPLIT]`/`[KDC-LOCKHOLD]`/`[KDC-ENTRY-SPLIT]` **均 0 行**、慢 `JsSendPacket` **0 条**、`THREAD_BLOCK` **0/0**、`maxHold=13ms`、`maxJsLockWait=0ms`、CPU 743ms/5.1s（健康稳态）⇒ 上一轮残留的 326~384ms 单次成本即**缓冲首次分配 + memset + 冷页故障**，已随 `105ddff` 消除；`n=` 探针因无现象而无内容可打（保留为后续长派发的诊断钩子）。
